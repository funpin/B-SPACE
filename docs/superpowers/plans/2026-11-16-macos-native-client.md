# Нативный macOS-клиент B:SPACE: план

Дата: 2026-11-16. Состояние репозитория: `a4850162` (2.3.2).

Исходные материалы, оба в `docs/superpowers/specs/`:

- `2026-11-14-macos-swift-port-webkit-audit.md` — аудит `WKWebView` и принятые после него решения;
- `2026-11-14-macos-swift-port-traceability.md` — матрица «поведение Electron → модуль Swift → тест».

Оба построены на коммите `7c7fd2a6` (1.11.0-f.1.1). С тех пор приложение ушло вперёд на 115 файлов, поэтому раздел 1 перечисляет, что в этих документах устарело, и остальной план опирается уже на текущий код. Ни одной строки Swift пока не написано; прототипы аудита лежали в ветке `prototype/desktop-macos-wkwebview-probes`, которой в `origin` нет (см. «Что нужно от владельца»).

Главное изменение не в коде, а в условиях: **веб-клиент теперь наш.** Задание запрещало трогать `packages/web`, и аудит поэтому решал всё подменой браузерных API из внедрённого скрипта (подмена `getDisplayMedia`, полифил `AudioContext.setSinkId`, угадывание CSS-классов для перетаскивания окна). Теперь то же делается явным контрактом в самом клиенте: меньше хрупкости, есть типы и тесты.

## 2. Принципы

1. **Портируется оболочка, а не интерфейс.** Интерфейс — веб-клиент, который отдаёт сервер. SwiftUI-версии экранов не будет.
2. **Движок — системный `WKWebView`**, минимальная macOS и схема захвата экрана — по решениям аудита (см. §3, там они вынесены на подтверждение владельцу).
3. **Явный контракт вместо подмены API.** Всё, что нативной оболочке нужно от страницы, оформляется как члены моста и ветки в `packages/web/src/platform/`, включаемые по наличию возможности, а не по названию платформы.
4. **Приложение и сервер версионируются независимо.** Новое приложение может открыть сервер со старым веб-клиентом, который про нативную оболочку не знает. Для него работает запасной режим (§5.5): приложение остаётся рабочим, часть возможностей упрощена. Обратное тоже верно: новый клиент в Electron и в браузере ведёт себя как сейчас.
5. **Один источник истины для моста.** Список каналов и их вид (fire, invoke, подписка, есть ли отписка) выносится в один файл, из которого берут данные и `preload.ts`, и сборка Swift-оболочки. Расхождение становится ошибкой сборки, а не находкой на проде.
6. **Windows остаётся на Electron.** `packages/desktop` не ломается; общие ресурсы (`instance-picker.html`, `recovery.html`, `update.html`, `games.json`, кадры трея) берутся из него, а не копируются.
7. **Отклонения записываются.** Любое место, где Swift-версия ведёт себя иначе, чем Electron, попадает в журнал отклонений (§8) с причиной.

## 4. Архитектура

```
packages/desktop-macos/
  Package.swift            SwiftPM: библиотеки чистой логики + исполняемая цель
  Sources/
    BSpaceCore/            чистая логика без AppKit, покрыта тестами
    BSpaceApp/             AppKit, WebKit, ScreenCaptureKit, CoreGraphics
  Tests/BSpaceCoreTests/
  Resources/bridge.js      шим моста, собирается из общего описания контракта
  scripts/bundle.sh        .app из результата `swift build`: Info.plist, ресурсы, подпись, проверка
  scripts/package.sh       DMG, zip, latest-mac.yml
```

- **Сборка без проекта Xcode.** `swift build -c release` и скрипт, который собирает бандл. Генератор проектов не нужен, сборка одинаковая локально и в CI, работает на Command Line Tools.
- **Версия** читается из корневого `package.json` при сборке.
- **Подпись** — тот же `.p12` из секретов `MAC_SIGN_P12`; логика `macSign.js` (временная связка ключей, проверка, что требование подписи называет хеш сертификата) переносится в `bundle.sh`.
- **`BSpaceCore`** повторяет декомпозицию TypeScript из матрицы (§1–§7 матрицы) плюс новое: `TrayState`, `TrayContext`, `UpdateReadyGate`, `UpdateWindowModel`, `PointerOverlayModel`, `AudioRouters`, `AppIdentity`.
- **Мост.** `WKUserScript` на старте документа, только главный фрейм; `WKScriptMessageHandlerWithReply`; один маршрутизатор с именами каналов как в `main.ts`. Сообщения не из главного фрейма отклоняются для всех каналов.
- **Зависимости:** ни одной сторонней. Читатель LevelDB для импорта `localStorage` и разбор YAML ленты пишутся под свою задачу (форматы узкие).

## 5. Совместимость

### 5.1. Контракт `window.backspace`

- 59 членов по текущему `preload.ts`; семантика (что возвращает `undefined`, что `Promise`, где есть отписка) — как в матрице §1, с дополнением для восьми новых.
- `packages/desktop/src/bridgeContract.ts` — новый файл-описание контракта. `preload.ts` строится по нему; из него же генерируется таблица для `bridge.js`. Тест в `packages/desktop` проверяет, что `preload.ts` не объявляет ничего сверх описания.
- Тест соответствия: HTML-харнесс вызывает каждый член и записывает форму результата; прогон в Electron и в Swift-оболочке, сравнение с эталонным файлом.
- Второй мост `window.bspaceUpdate` для окна обновления — тем же способом.

### 5.2. Данные пользователя

- Те же файлы в `~/Library/Application Support/Backspace/` в тех же форматах (матрица §5). Запись атомарная для всех файлов (решение 1 из §8 матрицы).
- **`localStorage`.** Одноразовый импорт из профиля Chromium (`Local Storage/leveldb`) для origin сохранённого сервера и подключённых серверов федерации, до первой загрузки страницы. Профиль Electron только читается: откат на Electron-сборку остаётся возможным. Проверить отдельно, лежит ли что-то заметное пользователю в IndexedDB (черновики, дескрипторы файлов в `idbHandles.ts`).
- Координаты окна: `window-state.json` хранит систему Electron (начало сверху слева, Y вниз), AppKit считает снизу. Двусторонняя конвертация с тестами на нескольких конфигурациях мониторов.

### 5.3. Идентичность и разрешения

Тот же `CFBundleIdentifier`, тот же сертификат, схема `backspace://`, категория, `CFBundleDisplayName = B:SPACE`, описания доступа к микрофону, камере и звуку. Сравнить `Info.plist` собранного Electron 2.3.2 с новым по всем ключам.

### 5.4. Обновления

- Лента `latest-mac.yml` остаётся в формате electron-updater: её читают и установленные Electron-копии, и новая оболочка.
- Модель статусов (`UpdateStatus`, `UpdateSnapshot`, `shouldPromptForUpdate`), расписание (10 с, затем 4 ч), отказ от версии, гейт готовности, прогресс в Dock, окно обновления — один в один.
- Установка: вспомогательный процесс ждёт выхода приложения, проверяет подпись нового бандла, заменяет старый, запускает новый. Сторож на 4 с и сообщения об ошибке — как сейчас.

### 5.5. Серверы со старым веб-клиентом

| Возможность | Сервер с поддержкой нативной оболочки | Старый сервер |
|---|---|---|
| Перетаскивание окна | Клиент сообщает прямоугольники через мост | Верхняя полоса 32 px (с учётом масштаба интерфейса) плюс известные классы `.titlebar-drag` |
| Демонстрация экрана | Сетка источников в приложении, нативный захват 60 кадров/с | Системный диалог выбора WebKit (`getScreenSharePickerMode() → 'system'`), 30 кадров/с, без звука системы |
| Устройство вывода | Выбор работает | Системное устройство по умолчанию |
| Трей, указатели | Работают | Клиент до этих функций их и в Electron не вызывает |

Оболочка узнаёт, с каким клиентом имеет дело, по вызову нового члена моста при загрузке страницы (клиент сообщает, какие возможности нативной оболочки он понимает).

Все аддитивные и включаются по наличию возможности. В Electron и в браузере поведение не меняется.

| # | Что | Где | Зачем |

Сервер менять не нужно.

## 7. Дизайн

Решение аудита — вариант A, паритет с Electron. Оно остаётся: пользователь не должен заметить смену оболочки.

- **Окно.** 1280×800, минимум 940×500, скрытый заголовок с системными кнопками на прежнем месте (сверить по скриншоту 2.3.2 до пикселя). Веб-клиент резервирует 33 px (`--titlebar-inset`), делённые на масштаб интерфейса. Фон окна и область под страницей — цвет чата «Камня», без вспышки при запуске.
- **Перетаскивание.** Нативный слой получает прямоугольники и делает `performDrag(with:)`; двойной клик по заголовку — по системной настройке. Клики в зонах без перетаскивания не перехватываются.
- **Трей.** Те же 16 шаблонных PNG из `packages/desktop/resources` (`tray-<кадр>Template.png`, `@2x`), те же длительности кадров из `TRAY_ANIMATIONS`, то же меню в том же порядке на пяти языках. При «Уменьшить движение» анимация стоит — сверить с Electron.
- **Окно обновления, выбор сервера, восстановление** — те же HTML-файлы.
- **Контекстное меню** `WKWebView` подавляется (в Electron его нет); автозамена, умные кавычки и тире выключены, проверка орфографии — как в Electron.
- **Указатели на стриме** — рисуются тем же способом и теми же цветами; окно исключается из захвата фильтром ScreenCaptureKit.
- **Меню приложения** — как `buildAppMenuTemplate` сейчас, включая пункт инструментов разработчика (см. отклонение в §8).
- **Чего не делаем:** нативных панелей, вибрации материала окна, системных тулбаров. Это вариант B/C аудита — отдельное решение после паритета.

Визуальная проверка: скриншоты ключевых экранов Electron 2.3.2 и Swift-сборки при одинаковом размере окна, сравнение с согласованным допуском (сглаживание шрифтов в WebKit и Chromium отличается).

## 9. Этапы

Каждый этап — отдельная ветка и pull request; после каждого — отчёт: что сделано, что проверено, что осталось.

**Этап 0. Доаудит (несколько дней, кода приложения нет).**
Перепрогнать стенд аудита на веб-клиенте 2.3.2: «Камень» (стекло, масштаб 50–250 %), стикеры, плитки голосового канала, сервис-воркер. Проверить `encoderImplementation` и логику «Авто» в WebKit. Открыть веб-клиент тестового сервера в Safari и пройти голос и просмотр стрима против Chromium (открытый пункт 3 аудита; Swift-код для этого не нужен). Обновить матрицу до 59 членов и 289 тестов.
*Готово, когда:* в аудите нет пунктов с пометкой «память» по темам, от которых зависят этапы 1–3.

**Этап 1. Каркас.**
Пакет, сборка, подпись, окно с `WKWebView`, загрузка сервера, выбор сервера, политика навигации, ядро моста (fire, invoke, события), `bridgeContract.ts`, харнесс теста контракта, User-Agent, очистка кеша при запуске.
*Готово, когда:* можно войти на живой сервер и переписываться; тест контракта проходит для реализованных каналов.

**Этап 2. Данные и жизненный цикл.**
Файлы настроек, импорт `localStorage`, состояние окна, единственный экземпляр, `backspace://`, автозапуск и скрытый старт, уведомления и бейдж, меню приложения, локализация, режим восстановления (включая сторож зависания), области перетаскивания (правка клиента №2).
*Готово, когда:* установка поверх Electron 2.3.2 сохраняет вход, настройки, размер окна и автозапуск.

**Этап 3. Трей, активность, сочетания клавиш.**
Анимированный трей и его меню, определение игры, глобальные сочетания через `CGEventTap`, таблица кодов клавиш с проверкой хешей против TypeScript, выяснение нужного разрешения.
*Готово, когда:* рация работает при неактивном окне без двойных срабатываний.

**Этап 4. Голос и демонстрация экрана.**
Разрешения микрофона и камеры, вывод звука (правка №3), перечисление источников и миниатюры, захват ScreenCaptureKit → H.264 → локальный `wss://` → страница (правки №4, №5), звук системы, окно указателей.
Первым делом — эксперимент по исключению собственного звука: захват звука через ScreenCaptureKit с исключением своего приложения (система сама относит звук служебных процессов WebKit к приложению — это гипотеза, её и проверяем); если не подтвердится — process tap Core Audio из открытого пункта 1 аудита.
Измерить: кадров/с, задержку, загрузку процессора и память на 1080p60, 1440p60 и родном разрешении против Electron 2.3.2.
*Готово, когда:* стрим со звуком смотрится из Chromium-клиента и наоборот; цифры записаны.

**Этап 5. Обновления и релиз.**
Определение возможности обновления, лента, загрузка, установщик, окно обновления, переход Electron → Swift на тестовой ленте, `release.yml` (ветка macOS: `swift build`, бандл, подпись, проверка, DMG, zip, `latest-mac.yml` с `minimumSystemVersion`), метка `desktop-build` для тестовых сборок.
*Готово, когда:* Electron 2.3.2 обновляется до Swift-сборки сам, а Swift-сборка — до следующей.

**Этап 6. Паритет и документация.**
Эталон теста контракта, ручной чек-лист (из задания §5, дополненный треем, окном обновления и указателями), визуальное сравнение, цифры производительности, `docs/systems/desktop-macos.md`, правки `desktop.md`, `desktop-security.md`, `voice.md`, журнал отклонений с отметками владельца.

**Этап 7. Выпуск.**
Сначала тестовая сборка по метке для владельца и товарища, затем релиз. Electron-ветка macOS в `release.yml` убирается только после того, как Swift-сборка прошла один полный цикл обновления у реальных пользователей.

## 10. Риски

| Риск | Чем закрываем |
|---|---|
| Двойное кодирование стрима хуже Electron по качеству или нагрузке | Измерение на этапе 4. Запасные варианты, которые открывает владение клиентом: подмена закодированных кадров через `RTCRtpScriptTransform` или публикация стрима нативным клиентом LiveKit под отдельным участником (требует правок сервера и клиента — отдельный проект) |
| Собственный звук попадает в стрим | Эксперимент в начале этапа 4; при неудаче — честный ответ `'included'` из `getSystemAudioCapability`, клиент уже умеет показывать это предупреждение |
| Выбор устройства вывода ломает эхоподавление | Проверка на живом звонке на этапе 4; при неудаче — деградация до системного устройства, запись в журнал |
| WebRTC WebKit ↔ Chromium через LiveKit | Проверка в Safari на этапе 0, до написания кода |
| Переход с Electron ломает установку у части пользователей | Тестовая лента на этапе 5; `minimumSystemVersion`; Electron-сборка остаётся в релизах |
| Потеря сертификата подписи | Уже описано в `desktop-security.md`: копия `.p12` у владельца вне репозитория |
| Импорт `localStorage` из LevelDB читает не всё | Тесты на реальном профиле; при неудаче импорта пользователь входит заново, данные сервера не теряются |
| Мост расходится между Electron и Swift | `bridgeContract.ts` и тест контракта в CI |

## 11. Что считается готовым

1. Тесты `BSpaceCore` покрывают все перенесённые кейсы TypeScript плюс новое (координаты окна, LevelDB, коды клавиш и хеши, сравнение версий, разбор ленты, политика навигации, гейт готовности, кадры трея).
2. Тест контракта даёт одинаковый результат в Electron и в Swift-оболочке.
3. Чек-лист пройден на поддерживаемых версиях macOS.
4. Память и процессор в простое и в звонке с демонстрацией — не хуже Electron 2.3.2, цифры приложены.
5. Документация и журнал отклонений обновлены, каждое отклонение одобрено владельцем.
