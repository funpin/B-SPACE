# Нативный macOS-клиент B:SPACE: план

Дата: 2026-11-16. Состояние репозитория: `a4850162` (2.3.2).

Исходные материалы, оба в `docs/superpowers/specs/`:

- `2026-11-14-macos-swift-port-webkit-audit.md` — аудит `WKWebView` и принятые после него решения;
- `2026-11-14-macos-swift-port-traceability.md` — матрица «поведение Electron → модуль Swift → тест».

Оба построены на коммите `7c7fd2a6` (1.11.0-f.1.1). С тех пор приложение ушло вперёд на 115 файлов, поэтому раздел 1 перечисляет, что в этих документах устарело, и остальной план опирается уже на текущий код. Ни одной строки Swift пока не написано; прототипы аудита лежали в ветке `prototype/desktop-macos-wkwebview-probes`, которой в `origin` нет (см. «Что нужно от владельца»).

Главное изменение не в коде, а в условиях: **веб-клиент теперь наш.** Задание запрещало трогать `packages/web`, и аудит поэтому решал всё подменой браузерных API из внедрённого скрипта (подмена `getDisplayMedia`, полифил `AudioContext.setSinkId`, угадывание CSS-классов для перетаскивания окна). Теперь то же делается явным контрактом в самом клиенте: меньше хрупкости, есть типы и тесты.

## 2. Принципы

1. **Портируется оболочка, а не интерфейс.** Интерфейс — веб-клиент, который отдаёт сервер. SwiftUI-версии экранов не будет.
2. **Движок — системный `WKWebView`**, минимальная macOS и схема захвата экрана — по решениям аудита (см. §3, там они вынесены на подтверждение владельцу).
3. **Явный контракт вместо подмены API.** Всё, что нативной оболочке нужно от страницы, оформляется как члены моста и ветки в `packages/web/src/platform/`, включаемые по наличию возможности, а не по названию платформы.
4. **Приложение и сервер версионируются независимо.** Новое приложение может открыть сервер со старым веб-клиентом, который про нативную оболочку не знает. Для него работает запасной режим (§5.5): приложение остаётся рабочим, часть возможностей упрощена. Обратное тоже верно: новый клиент в Electron и в браузере ведёт себя как сейчас.
5. **Один источник истины для моста.** Список каналов и их вид (fire, invoke, подписка, есть ли отписка) выносится в один файл, из которого берут данные и `preload.ts`, и сборка Swift-оболочки. Расхождение становится ошибкой сборки, а не находкой на проде.
6. **Windows остаётся на Electron.** `packages/desktop` не ломается; общие ресурсы (`instance-picker.html`, `recovery.html`, `update.html`, `games.json`, кадры трея) берутся из него, а не копируются.
7. **Отклонения записываются.** Любое место, где Swift-версия ведёт себя иначе, чем Electron, попадает в журнал отклонений (§8) с причиной.

## 4. Архитектура

```
packages/desktop-macos/
  Package.swift            SwiftPM: библиотеки + исполняемые цели
  Sources/
    BSpaceCore/            чистая логика без AppKit, покрыта тестами
    BSpaceShell/           AppKit, WebKit, ScreenCaptureKit, CoreGraphics: окно, вид, мост
    BSpaceApp/             само приложение: запускает BSpaceShell
    ContractCheck/         прогоняет BSpaceShell через тест контракта моста
  Tests/BSpaceCoreTests/
  contract/harness.html    страница теста контракта
  scripts/bundle.sh        .app из результата `swift build`: Info.plist, ресурсы, подпись, проверка
  scripts/contract-check.sh  запуск теста контракта
  scripts/package.sh       DMG, zip, latest-mac.yml (этап 5)
```

- **Сборка без проекта Xcode.** `swift build -c release` и скрипт, который собирает бандл. Генератор проектов не нужен, сборка одинаковая локально и в CI, работает на Command Line Tools.
- **Версия** читается из корневого `package.json` при сборке.
- **Подпись** — тот же `.p12` из секретов `MAC_SIGN_P12`; логика `macSign.js` (временная связка ключей, проверка, что требование подписи называет хеш сертификата) переносится в `bundle.sh`.
- **`BSpaceCore`** повторяет декомпозицию TypeScript из матрицы (§1–§7 матрицы) плюс новое: `TrayState`, `TrayContext`, `UpdateReadyGate`, `UpdateWindowModel`, `PointerOverlayModel`, `AudioRouters`, `AppIdentity`.
- **Мост.** `WKUserScript` на старте документа, только главный фрейм; `WKScriptMessageHandlerWithReply`; один маршрутизатор с именами каналов как в `main.ts`. Сообщения не из главного фрейма отклоняются для всех каналов. Скрипт страницы не лежит отдельным файлом `bridge.js`, а строится при запуске из описания контракта (`BridgeScript`): сгенерированной копии, которая могла бы отстать, нет.
- **Оболочка — библиотека, а не исполняемая цель.** `BSpaceShell` подключают и приложение, и `ContractCheck`: тест контракта идёт на тех же окне, конфигурации вида и мосте, что и у пользователя, а в выпускаемом бинарнике нет отладочных флагов.
- **Сборка для разработки отделена от установленного приложения.** `bundle.sh` по умолчанию даёт бандлу свой идентификатор (`com.backspace.desktop.dev`) и свою папку настроек (`Backspace-Dev`, ключ `BSpaceUserDataDirectory` в `Info.plist`) и не регистрирует `backspace://`. Идентичность выпускаемого приложения включается явно: `--identity release`.
- **Зависимости:** ни одной сторонней. Читатель LevelDB для импорта `localStorage` и разбор YAML ленты пишутся под свою задачу (форматы узкие).

## 5. Совместимость

### 5.1. Контракт `window.backspace`

- 59 членов по текущему `preload.ts`; семантика (что возвращает `undefined`, что `Promise`, где есть отписка) — как в матрице §1, с дополнением для восьми новых.
- `packages/desktop/src/bridgeContract.json` — описание контракта: члены обоих мостов, вид каждого (`value`, `fire`, `invoke`, `subscribe`), канал, есть ли отписка. Это JSON, а не TypeScript, чтобы Swift-сборка читала тот же файл без генерации; `bridgeContract.ts` его разбирает и типизирует. **Сделано на этапе 1.**
- `preload.ts` по описанию не строится: изолированный preload не может подключить локальный модуль (это уже отмечено в `updatePreload.ts`). Вместо этого `bridgeContract.test.ts` читает исходник обоих preload компилятором TypeScript и падает при любом расхождении с описанием, в обе стороны; он же проверяет, что каждый канал описания известен главному процессу и что у главного окна нет обработчика вне описания.
- Тест соответствия: `contract/harness.html` читает и вызывает каждый член и записывает форму результата; `ContractCheck` прогоняет её на настоящей оболочке и сверяет с тем, что обещает описание. **Сделано на этапе 1 для Swift-оболочки.** Прогон той же страницы в Electron и сравнение форм ответов с эталонным файлом — этап 6.
- Каналы, чья функция ещё не перенесена, отвечают так, как Electron отвечает там, где этой функции нет (`InterimReplies`, по этапам): веб-клиент вызывает почти весь мост при каждом запуске, и отклонённый вызов внутри эффекта роняет клиент целиком. Перенос канала — это регистрация обработчика и удаление записи из таблицы в одном изменении; тест не даёт им разойтись с описанием.
- Второй мост `window.bspaceUpdate` для окна обновления — тем же способом; в описании он уже есть.

### 5.2. Данные пользователя

- Те же файлы в `~/Library/Application Support/Backspace/` в тех же форматах (матрица §5). Запись атомарная для всех файлов (решение 1 из §8 матрицы).
- **`localStorage`.** Одноразовый импорт из профиля Chromium (`Local Storage/leveldb`) для origin сохранённого сервера и подключённых серверов федерации, до первой загрузки страницы. Профиль Electron только читается: откат на Electron-сборку остаётся возможным. Проверить отдельно, лежит ли что-то заметное пользователю в IndexedDB (черновики, дескрипторы файлов в `idbHandles.ts`).
- Координаты окна: `window-state.json` хранит систему Electron (начало сверху слева, Y вниз), AppKit считает снизу. Двусторонняя конвертация с тестами на нескольких конфигурациях мониторов.

### 5.3. Идентичность и разрешения

Тот же `CFBundleIdentifier`, тот же сертификат, схема `backspace://`, категория, `CFBundleDisplayName = B:SPACE`, описания доступа к микрофону, камере и звуку, из ключей App Transport Security — один `NSAllowsArbitraryLoads` (без него инстанс по `http://` с доменным именем не откроется; `NSAllowsLocalNetworking` из бандла Electron не переносится, потому что рядом с ним система первый ключ игнорирует — доаудит, §2.7). Эталонный список ключей `Info.plist` Electron 2.3.2, с пометками, что переносится, — в доаудите, §4.2.

### 5.4. Обновления

- Лента `latest-mac.yml` остаётся в формате electron-updater: её читают и установленные Electron-копии, и новая оболочка.
- Модель статусов (`UpdateStatus`, `UpdateSnapshot`, `shouldPromptForUpdate`), расписание (10 с, затем 4 ч), отказ от версии, гейт готовности, прогресс в Dock, окно обновления — один в один.
- Установка: вспомогательный процесс ждёт выхода приложения, проверяет подпись нового бандла, заменяет старый, запускает новый. Сторож на 4 с и сообщения об ошибке — как сейчас.

### 5.5. Серверы со старым веб-клиентом

| Возможность | Сервер с поддержкой нативной оболочки | Старый сервер |
|---|---|---|
| Перетаскивание окна | Клиент сообщает прямоугольники через мост | Верхняя полоса 32 pt (отклонение 25) |
| Демонстрация экрана | Сетка источников в приложении, нативный захват 60 кадров/с | Системный диалог выбора WebKit (`getScreenSharePickerMode() → 'system'`), 30 кадров/с, без звука системы |
| Устройство вывода | Выбор работает | Системное устройство по умолчанию |
| Трей, указатели | Работают | Клиент до этих функций их и в Electron не вызывает |

Оболочка узнаёт, с каким клиентом имеет дело, по вызову нового члена моста при загрузке страницы (клиент сообщает, какие возможности нативной оболочки он понимает).

## 7. Дизайн

Решение аудита — вариант A, паритет с Electron. Оно остаётся: пользователь не должен заметить смену оболочки.

- **Окно.** 1280×800, минимум 940×500, скрытый заголовок с системными кнопками на прежнем месте (сверить по скриншоту 2.3.2 до пикселя). Веб-клиент резервирует 33 px (`--titlebar-inset`), делённые на масштаб интерфейса. Фон окна и область под страницей — цвет чата «Камня», без вспышки при запуске.
- **Перетаскивание.** Нативный слой получает прямоугольники и делает `performDrag(with:)`; двойной клик по заголовку — по системной настройке. Клики в зонах без перетаскивания не перехватываются.
- **Трей.** Те же 16 шаблонных PNG из `packages/desktop/resources` (`tray-<кадр>Template.png`, `@2x`), те же длительности кадров из `TRAY_ANIMATIONS`, то же меню в том же порядке на пяти языках. При «Уменьшить движение» анимация стоит — сверить с Electron.
- **Окно обновления, выбор сервера, восстановление** — те же HTML-файлы.
- **Контекстное меню** `WKWebView` подавляется (в Electron его нет). Замена кавычек, тире, текста и автоисправление выключаются четырьмя ключами настроек до создания вида, иначе `WKWebView` меняет набранный текст; проверка орфографии включается, грамматики — выключается, как в Electron (ключи и замер — доаудит, §2.4).
- **Указатели на стриме** — рисуются тем же способом и теми же цветами; окно исключается из захвата фильтром ScreenCaptureKit.
- **Меню приложения** — как `buildAppMenuTemplate` сейчас, включая пункт инструментов разработчика (см. отклонение в §8).
- **Чего не делаем до паритета:** нативных панелей, материалов окна, системных тулбаров. Это следующий шаг, а не отказ: владелец решил (2026-11-16), что у Swift-клиента будет свой интерфейс в стиле Liquid Glass — этап 8 в §9. Паритет идёт первым, чтобы переход с Electron проверялся на неизменном интерфейсе, а новый вид появился отдельным обновлением.

Визуальная проверка: скриншоты ключевых экранов Electron 2.3.2 и Swift-сборки при одинаковом размере окна, сравнение с согласованным допуском (сглаживание шрифтов в WebKit и Chromium отличается).

Клиент, запущенный из терминала, будет слышать себя в собственном стриме; для сборок разработки это надо помнить. Список включённых приложений (все, кроме своего) тоже убирает свой звук, причём в обоих случаях, но теряет звук всего, что не приложение, и требует добавлять приложения, запущенные после начала захвата; он остаётся запасным вариантом. **Не проверено:** дорожка, пришедшая по WebRTC (на этой машине два соединения внутри страницы не соединились из-за туннеля; вместо неё проверен живой поток в аудиоэлементе, которым дорожка звонка и воспроизводится) — подтвердить звонком на тестовом сервере; флаг `excludesCurrentProcessAudio` у приложения, запущенного обычным способом (нужно собственное разрешение инструмента на запись экрана); то же на самом клиенте, когда появится его захват. Цифры и таблица — в README пакета, раздел CaptureProbe. **Разрешения на микрофон и камеру:** оболочка отвечает на запрос веб-вида сама (`MediaCapturePolicy`): странице окна — да, вложенному фрейму и собственным страницам оболочки — нет (отклонение 34); пользователь видит один системный запрос вместо двух. Проверено тестами логики; системный запрос и работающие микрофон с камерой на собранном приложении не проверены. **Устройство вывода (правка клиента №3):** в веб-клиенте появился `OutputRouter` (`audio/outputRouter.ts`): там, где у `AudioContext` нет `setSinkId` (WebKit, Firefox), общий звук уходит в `<audio>` с `setSinkId`, но только для устройства не по умолчанию; в Chromium всё как было. Раздел настроек больше не пишет «браузер не поддерживает»: он либо есть, либо скрыт. Замер на `WKWebView` (macOS 27.2.1): `HTMLMediaElement.setSinkId` есть, выбор динамиков включён, а настройка WebKit, требующая жеста для выбора динамика, включена по умолчанию; поэтому вызов делается прямо из обработчика щелчка, а сохранённый выбор, отклонённый при запуске, применяется при первом нажатии. Проверено тестами (18 случаев); на настоящих устройствах не проверено: нужен выданный доступ к микрофону (без него WebKit не перечисляет устройства вывода) и человек, который слышит результат. Эхоподавление при выводе через `<audio>` не измерено. **Список источников:** `get-screen-sources` отвечает настоящим списком (`SystemScreenSourceLister`, ScreenCaptureKit): экраны и обычные окна с миниатюрами до 320×180 и значками приложений, в формате Electron-сборки, с её же правилом — новые снимки только для окна в фокусе и не чаще раза в секунду. Проверено тестами логики, на оболочке с придуманным списком (`--check sources`, в `contract-check.sh`) и одним настоящим запросом к системе (`--check sources-system`: 1 экран и 5 окон за 0,44 с, 258 КБ JSON). Настоящий запрос нашёл дефект: при включённом Stage Manager система перечисляет копии окон из его полосы как обычные окна с заголовками, и список удваивался (15 окон вместо 5); окна системной обстановки теперь отбрасываются. Замечено: окно, стоящее в полосе Stage Manager, система показывает в его уменьшенном размере; что придёт в захвате такого окна, надо смотреть, когда появится захват. Веб-клиент список пока не запрашивает: режим выбора остаётся `'system'`, пока оболочка не умеет захватывать выбранное. **Локальный канал** (решение 4 аудита; ветки с прототипами нет, поэтому проверено заново): `LocalMediaChannel` — WebSocket поверх TLS на `127.0.0.1` со случайным портом. Сертификат каждый канал делает себе сам (`LocalIdentity`: ключ P-256, сертификат на адрес `127.0.0.1`, DER и файл PKCS#12 пишет сам пакет) и отдаёт системе в память (`kSecImportToMemoryOnly`, macOS 15): связка ключей не затрагивается, на диск ничего не пишется. Доверяет сертификату только веб-вид оболочки и только при совпадении адреса, порта открытого канала и самого сертификата байт в байт. Говорить по каналу может тот, кто первым сообщением назвал одноразовый токен; рукопожатие с чужого origin отклоняется; канал живёт, пока окно показывает ту же страницу. Проверено тестами логики (в том числе: система принимает файл и отдаёт тот же сертификат, проверка доверия проходит только для `127.0.0.1` и только в срок действия, вывод ключа совпал с эталоном другой реализации) и на оболочке (`--check media-channel`, в `contract-check.sh`): неверный токен и повторное подключение закрываются, чужому каналу страница не доверяет, 240 сообщений по 40 КБ при 60 в секунду доходят за 0,2 мс по медиане и 1,8 мс на 95-м перцентиле (в аудите — 0,2 и 1,8); со страницы с origin `https` на стенде — 0,5 и 3,1 мс. Политика CSP сервера подключение разрешает (`connect-src wss:`), сервер менять не нужно. **Кодировщик и формат сообщений:** `VideoEncoder` (VideoToolbox, H.264 High, аппаратный, без перестановки кадров, около 0,12 бита на пиксель: 15 Мбит/с на 1080p60, 27 на 1440p60, 43 на 3024×1964) и `MediaWire` (текстовое сообщение JSON с форматом для `VideoDecoder.configure`, двоичное сообщение с кадром: байт вида, время захвата, блок доступа H.264; страница может попросить опорный кадр). Замеры разошлись с прототипом аудита в двух местах. **Первое:** режим малой задержки (`EnableLowLatencyRateControl`), который аудит называл обязательным, на macOS 27.2.1 выбирает другой кодировщик (`h264.rtvc` вместо аппаратного `ave.avc`): он держит вызов по 25–32 мс на кадр и выдаёт 39 кадров/с на 1080p, 34 на 1440p и 29 на 3024×1964 при поданных 60, с задержкой внутри до 163 мс. Аппаратный кодировщик без этого режима держит 60 кадров/с на всех трёх размерах с задержкой 18, 23 и 35 мс. Режим малой задержки не используется. **Второе:** аппаратный кодировщик кадры не переставляет, но в потоке об этом не говорит, и декодер WebKit, которому не сказали, придерживает столько кадров, сколько позволяет уровень: 4 на 1080p, 12 на 1440p, 7 на 3024×1964 (медиана задержки 90, 230 и 161 мс). Оболочка дописывает в набор параметров последовательности (SPS) ограничение потока с нулём переставляемых кадров (`H264ParameterSets`: разбор и переписывание SPS, тесты на настоящих наборах аппаратного кодировщика); смена профиля не помогает. **Сквозной замер** (`--check video-pipe`, запускается руками, меряет аппаратный кодировщик этой машины): 300 кадров, нарисованных самой проверкой, 60 в секунду → кодировщик → канал → воркер страницы (`VideoDecoder` → `VideoTrackGenerator`) → дорожка в `<video>`. В странице 60 кадров/с; от создания кадра до декодирования после первой секунды, по нескольким прогонам на занятой машине (средняя нагрузка 10–17): медиана 23–26 мс и 95-й перцентиль 36–63 мс на 1080p, 28–31 и 40–79 мс на 1440p, 42–46 и 51–115 мс на 3024×1964 (в аудите с простыми кадрами — 11/16, 16/18 и 31/69). 95-й перцентиль — в основном опорный кадр, который страница просит посреди прогона. **Третья находка:** на пути кадра никто ничего не выбрасывает, поэтому декодер, отставший на мгновение, остаётся отставшим навсегда: на 3024×1964 в одном прогоне из трёх в очереди декодера копилось 30 кадров и задержка доходила до 0,8 с. Читающая сторона теперь следит за очередью декодера: больше четырёх кадров — сброс декодера, запрос опорного кадра и пропуск всего, что пришло до него; в таких прогонах (один раз за прогон, 10–11 кадров из 300) самый поздний кадр опаздывал на 0,16–0,22 с. Так делает страница проверки; то же должен делать читатель в веб-клиенте (правка №4). Это синтетические кадры: настоящий захват экрана, загрузка процессора и сравнение с Electron не измерены. **Захват экрана:** `SystemScreenCapturer` (ScreenCaptureKit: экран по идентификатору или отдельное окно) и `CaptureSession`, который связывает захват, кодировщик и канал. Три новых члена моста только для нативной оболочки: `startNativeScreenCapture({ sourceId, maxWidth, maxHeight, frameRate })` отвечает адресом канала, токеном, размером и частотой видео либо причиной отказа; `stopNativeScreenCapture()`; `onNativeScreenCaptureEnded` — захват кончился сам (окно закрыли, экран отключили, разрешение забрали). Размер видео — собственный размер источника в пикселях, вписанный в запрошенный (экран 3456×2234 при запросе 1080p даёт 1670×1080). Кто выбирает источник, решает сам клиент: `getScreenSharePickerMode({ nativeCapture: true })` отвечает `'app'`, без аргумента — `'system'`, поэтому сервер со старым веб-клиентом получает системный диалог WebKit (§5.5), а отдельного вызова «что я умею» не понадобилось. Неподвижный экран: система шлёт кадр только при изменении, поэтому сеанс хранит последний кадр и кодирует его заново опорным, если страница подключилась позже или её декодер попросил опорный кадр. Проверено тестами логики, на оболочке с придуманным экраном (`--check capture`, в `contract-check.sh`: запуск через мост, отказы, неподвижный экран, три способа завершения) и **настоящим захватом** основного экрана через весь путь (`--check capture-system`, руками): за 5 секунд обычной работы на экране страница декодировала 249 кадров, 51,5 в секунду пока экран менялся, от захвата до декодирования 20 мс по медиане, 38 мс на 95-м перцентиле, 59 мс максимум, ни одного пропущенного кадра. Размер фиксируется при старте: окно, изменённое позже, масштабируется в него. Загрузка процессора и сравнение с Electron не измерены. **Несколько захватов сразу:** при смене источника во время идущей демонстрации экран настройки сначала показывает превью нового источника, а смена размера запускает новый захват раньше, чем останавливает старый; при одном захвате на оболочку живая демонстрация обрывалась бы. Поэтому у каждого захвата свой идентификатор: `startNativeScreenCapture` его возвращает, `stopNativeScreenCapture(id)` и событие окончания его называют; одновременно не больше четырёх. **Правка клиента №4 сделана:** `packages/web/src/platform/nativeCapture/` — `nativeScreenCapture.ts` (запуск захвата через мост, обычный поток с одной видеодорожкой), модульный воркер `reader.worker.ts` (`WebSocket` → `VideoDecoder` → `VideoTrackGenerator`) и его логика `channelReader.ts` с правилом «догнать». Остановка дорожки останавливает захват; захват, кончившийся сам, даёт дорожке событие `ended`; другой размер или частота — второй захват того же источника за той же дорожкой, без переопубликации. Три места, где клиент подгонял идущий захват под настройки, сведены в одну функцию `applyCaptureLimits`. Экран настройки стрима сообщает оболочке `nativeCapture: true` и берёт выбранную плитку через нативный захват вместо `getDisplayMedia`. Проверено тестами (26 новых: логика читателя и модуль с подставным воркером и мостом; весь набор веб-клиента зелёный) и **настоящим кодом клиента в оболочке** (`--check capture-web`, руками: нужен dev-сервер и страница-стенд `dev-native-capture.html`): дорожка играет в `<video>` в запрошенном размере, продолжает играть, после смены ограничений показывает новый размер при той же дорожке, сообщает об окончании захвата, останавливает захват при остановке, сообщает об исчезнувшем источнике. **Не проверено:** демонстрация в настоящем звонке (публикация дорожки через LiveKit и просмотр с другого клиента) — нужен вход на тестовый сервер из собранного приложения. **Звук системы (правка клиента №5) сделан.** Это отдельный захват, не часть захвата картинки: переключатель «Звук системы» включает и выключает его посреди стрима, а один фильтр ScreenCaptureKit не может оставить окно приложения в картинке и убрать его звук из записи. Оболочка (`SystemSoundCapturer`): поток ScreenCaptureKit со своим приложением в списке исключённых, 48 кГц, два канала; отсчёты идут по собственному локальному каналу сообщениями вида 3 (32-битные числа, кадр за кадром). Три новых члена моста только для нативной оболочки: `startNativeSystemAudio()` (адрес канала, токен, частота и число каналов либо причина отказа), `stopNativeSystemAudio(id)`, `onNativeSystemAudioEnded`. `getSystemAudioCapability({ nativeAudio: true })` отвечает `'excluded'`, любой другой аргумент — `'unavailable'`: сервер со старым веб-клиентом захватывает через WebKit, где звука системы нет. Веб-клиент (`platform/nativeCapture/nativeSystemAudio.ts`): воркер читает канал и передаёт отсчёты прямо в `AudioWorklet` через отдельный порт, минуя основной поток страницы; выход ворклета подключён только к потоку, в динамики ничего не идёт; буфер `PcmBuffer` держит запас 60 мс и при накоплении больше 250 мс пропускает старое. Дорожка добавляется к захвату при включённом «Звуке системы» и может быть добавлена или убрана посреди стрима, как в Electron. Проверено тестами (12 в пакете, 31 в веб-клиенте), на оболочке с придуманным звуком (`--check system-audio`, в `contract-check.sh`: тон 440 Гц слева и 880 Гц справа доходят до страницы на своих сторонах), настоящим кодом клиента в оболочке (`--check capture-web`: измеритель в странице слышит оба тона на дорожке на своих сторонах и с исходным уровнем) и **настоящим захватом** (`--check system-audio-system`, руками): система отдаёт 48 000 кадров в секунду кусками по 960 (20 мс), непрерывно, даже когда ничего не играет, не реже чем раз в 32 мс; самый старый отсчёт на момент чтения страницей — 50 мс; тихий тон 440 Гц, сыгранный страницей проверки с уровнем 0,003, слышен и в канале, и на дорожке клиента (0,0021, это его среднеквадратичное значение), в буфере клиента 27 мс, пропусков и опустошений нет. **Находка про скрытую страницу:** окно проверки никогда не показывается, а страницу, которую никто не видел около полуминуты, WebKit придерживает: таймеры в воркерах срабатывают десять раз в секунду, а часы звукового ворклета отстают от настоящих на 3–19 % (`--check audio-clock`, руками; первые полминуты часы идут точно при любой расстановке: один контекст или два сразу, с одной частотой или с разными, с воркером и без). Звук тогда копится в буфере и пропускается по пятой доле секунды. Страницу, которая играет слышимый звук, WebKit не придерживает (прогон с тоном шёл точно), а в звонке страница и захватывает микрофон, и играет собеседников; но проверено это не было, и при первом стриме в настоящем звонке надо смотреть именно на стрим из скрытого или заслонённого окна. **Не проверено и не сделано:** стрим со звуком в настоящем звонке; исключение собственного звука при захвате самим клиентом (эксперимент исключал приложение из захвата, который вёл другой процесс); удвоение звука при запущенном SoundSource (`getAudioRouters` по-прежнему отвечает пустым списком). (Примечание «нужна macOS 13 или новее», которое клиент показал бы на macOS 14, где нативного захвата нет, перестало быть вопросом: минимум — macOS 26, §3.) **Окно указателей сделано.** Члены моста те же, что в Electron-сборке (`setStreamPointerOverlay`, `endStreamPointerOverlay`), веб-клиент не менялся. Список проверяется по тем же правилам (`OverlayPointers.sanitized`: не больше 32, место внутри картинки, имя до 64 единиц, цвет только `rgb(…)`). Экран — тот, что показывает самый новый из идущих захватов целого экрана (`PointerOverlayTarget`); у демонстрации окна указателей нет, как в Electron. Окно (`SystemPointerOverlay`) — прозрачная неактивирующая панель во весь экран: поверх всего, на всех Spaces и над полноэкранными приложениями, вне Mission Control, клики проходят сквозь; стрелка, метка с именем и кольцо щелчка — тех же форм, размеров и длительностей, что в Electron. Из захвата панель убирается напрямую: захват экрана называет её в фильтре ScreenCaptureKit (номер окна подставляет оболочка, страница его задать не может). Проверено тестами логики (18), на оболочке с подставными экраном и окном (`--check pointer-overlay`, в `contract-check.sh`) и **на настоящем экране** (`--check pointer-overlay-system`, руками, три захвата основного экрана): окно, которое само от захвата не прячется, в обычном захвате видно, а в захвате, назвавшем его в фильтре, — нет, то есть фильтр работает сам по себе; окно в том виде, в каком его делает приложение, не видно и в захвате без фильтра (на macOS 27.2.1 ScreenCaptureKit учитывает и тип общего доступа окна, это страхует захват через системный диалог). Вид указателей сверен по картинке, нарисованной вне экрана. **Не проверено глазами на экране:** панель над полноэкранным приложением и при переходе между Spaces, при включённом Stage Manager, прохождение кликов; указатели настоящих зрителей в звонке. **Первая проба в настоящем звонке (2026-11-19, тестовый сервер с веб-клиентом этой ветки, Swift-сборка и Electron 2.3.2 на одном Mac, туннель включён):** при нажатии «Начать трансляцию» ведущего на Swift-сборке выкидывало из звонка. Две причины, обе в веб-клиенте и обе не связаны с захватом (то же было бы в Safari): (1) перед публикацией H.264 клиент переписывает профиль в SDP-предложении, чтобы Chromium взял аппаратный кодировщик; WebKit такое предложение отвергает («Failed to set local video description recv parameters»), согласование рвётся, LiveKit отключает участника. Теперь правка применяется только в Chromium (`hwOverdrive.appliesTo`). После этого стрим опубликовался без разрыва. (2) После публикации клиент выставляет потолок битрейта и частоты кадров вместе с приоритетами и предпочтением деградации; WebKit отвергает такой вызов целиком («Attempted to set an unimplemented parameter of RtpParameters»), и потолок не применялся. Теперь полный набор пробуется один раз, а отвергнувшему движку пишется только потолок. Чтобы увидеть это, в dev-сборку добавлена запись предупреждений и ошибок страницы в файл (`PageLog`, `Backspace-Dev/page.log`): системный журнал о происходящем внутри страницы ничего не говорит. **Что проба не показала:** шёл ли стрим через нативный захват или через захват WebKit (владелец видел кнопку «Выбрать» вместо плиток источников: вероятно, список пришёл пустым из-за отсутствия у сборки разрешения на запись экрана, не подтверждено); что видел зритель; вторая правка в звонке не проверена; звук системы, указатели и стрим из скрытого окна не пробовались. **Вторая проба в звонке (2026-11-19, образ из ветки с обоими исправлениями):** нативный захват подтверждён (зритель получал 1670×1080 — размер, который вписывает оболочка), H.264 согласован, указатели работают в обе стороны, звук системы есть, смена качества работает; запись ошибок страницы чистая. Найдено: (1) **стрим окна шёл мелкой размытой картинкой (314p).** При включённом Stage Manager окно, стоящее в боковой полосе, система сообщает уменьшенным, а размер захвата фиксировался при старте. Теперь захват окна следит за его размером: система прикладывает к каждому кадру место содержимого, масштаб и число пикселей на точку, по ним считается собственный размер окна; когда он меняется и держится 0,3 с, сеанс заводит кодировщик нового размера, сообщает странице новый формат и меняет размер потока. Проверено на оболочке с придуманным источником (`--check capture`) и на настоящем окне (`--check capture-window-system`, руками): видео стартует в размере окна (с заголовком), после увеличения окна система сообщает новый размер один раз, кадры идут в новом размере, лишних сообщений нет. Заодно дорожка нативного захвата теперь сообщает свой размер через `getSettings` (LiveKit писал «could not determine track dimensions»). В звонке это ещё не проверено. (2) **Swift-сборку трижды выкинуло из звонка:** в журнале LiveKit `dtls timeout`, сервер переставал её слышать. Пинг в Swift-сборке 90–160 мс против 5 мс в Electron на том же Mac. Причина не доказана; версия — трафик WebKit идёт через туннель владельца, а Chromium ходит напрямую. (3) Отправка шла 1670×1080 при 43 кадрах/с и 2,1 Мбит/с с пометкой «ограничено процессором»; своё превью у ведущего подвисало. **Планка приёмки, заданная владельцем 2026-11-19:** захват и трансляция в нативном клиенте должны быть не хуже, чем в Electron; хуже — не принимается. Сейчас планка не пройдена. Порядок работ: сначала сетевой путь WebKit (почему 90 мс и обрывы), затем замеры Swift против Electron на одном содержимом (кадры/с, разрешение, битрейт, загрузка), затем, если двойное кодирование (оболочка кодирует, страница декодирует и кодирует заново) окажется причиной отставания, — смена схемы на одно кодирование. **Решение владельца от 2026-11-19: двойное кодирование убрать, схему передачи стрима переписать** — оболочка сама отправляет стрим в звонок вторым соединением. План этой переделки — в разделе 12; пункты «локальный канал», «кодировщик», «правки клиента №4 и №5» выше описывают схему, которая уходит. **Дальше:** раздел 12.

## 12. Стрим из оболочки: одно кодирование (решение от 2026-11-19)

### 12.1. Почему

Первая схема этапа 4 доставляла картинку в звонок через страницу: оболочка захватывает и кодирует (H.264), страница декодирует и отдаёт кадры WebRTC, WebRTC кодирует их второй раз. В настоящем звонке это дало 43 кадра/с с пометкой «ограничено процессором» при том, что сам захват держит 60. Владелец: «двойное кодирование — это бред, весь смысл нативного приложения пропадает»; планка приёмки — захват и трансляция **не хуже Electron**, хуже не принимается; обходные приёмы («пустышки» с подменой кадров в странице) отклонены, код разрешено переписать.

Причина двойного кодирования не в захвате и не в сервере: соединение со звонком живёт в странице, а WebRTC в странице принимает только несжатые кадры. Значит, у оболочки должно быть своё соединение.

### 12.2. Схема

Оболочка подключается к комнате LiveKit **вторым участником — «стримом» пользователя** — через нативную библиотеку LiveKit для Swift и публикует две дорожки: экран (`screen_share`) и звук системы (`screen_share_audio`). Путь картинки: ScreenCaptureKit → кадр (`CVPixelBuffer`, без копирования) → аппаратный кодировщик внутри WebRTC библиотеки → сервер. Одно кодирование, как в Chromium. Страница в передаче картинки и звука стрима не участвует.

Голос (микрофон, воспроизведение собеседников) остаётся в странице, как сейчас. Соединений два: голос и стрим. Картинка и звук системы идут в одном соединении и потому синхронны между собой.

Что остаётся за страницей: кнопки и экран настройки стрима, состояние «в эфире», сигналы зрителям (`stream_stop`, `stream_republish`, `stream_resume`), приём указателей и запросов «смотрю», показ статистики. Страница решает, оболочка исполняет.

### 12.3. Сервер

LiveKit не пускает одного участника в комнату дважды, поэтому «стриму» нужен собственный пропуск.

- **Пропуск стрима.** `POST /api/livekit/token` принимает назначение (`purpose: 'stream'`; точное имя поля — при реализации) и выдаёт токен второго участника. Проверки те же, что у голосового токена (членство, `CONNECT`), плюс право `STREAM`; без него — отказ с новым кодом ошибки (`ErrorCode`, `localization.md`).
- **Права в токене:** вход в комнату, публикация только `SCREEN_SHARE` и `SCREEN_SHARE_AUDIO`; подписка, отправка данных и смена собственных метаданных запрещены. Срок на вход короткий, как у федеративного токена; дальше LiveKit продлевает сам.
- **Кто это.** Identity стрима отличается от identity пользователя так, чтобы первая часть не была идентификатором пользователя (например, `stream.<userId>:<username>`): старый клиент, разбирающий identity по двоеточию (`parseIdentity`), увидит отдельного участника с понятным именем, а не «того же пользователя дважды». Связь с владельцем сервер записывает в атрибуты участника в самом токене (`streamOf: <identity пользователя>`): клиент доверяет только им, подделать их участник не может (менять свои метаданные ему запрещено).
- **Федерация.** Тот же токен для звонков между серверами: `generateFederatedCallToken` (выдаётся в `ws/events.ts`) получает вариант для стрима; identity строится от `homeUserId`, как у голоса. Маршрутизация по источнику (`getApiForOrigin`) та же, что у голосового токена: пропуск выдаёт сервер, на котором идёт звонок.
- **Модерация.** Отключение, перенос и запрет стримить сегодня исполняет клиент по событию сервера (`voice_disconnected`, `voice_moved`): сервер участника из LiveKit не удаляет. Стрим подчиняется тем же событиям — страница останавливает его в оболочке. Принудительное удаление участника на стороне сервера — отдельная задача для обоих соединений, в эту переделку не входит; хуже, чем сейчас, не становится.
- **Данных и схемы БД не касается.** Меняются `routes/livekit.ts`, типы `LiveKitTokenRequest/Response` в `shared`, тесты маршрута, `docs/systems/api.md`, `voice.md`, `federation.md`, `permissions.md`.
- **Совместимость.** Сервер без этой правки на запрос пропуска стрима ответит ошибкой: клиент в нативной оболочке откатывается к захвату WebKit (системный диалог, как для старого веб-клиента, §5.5). Нужен признак в ответе сервера, а не угадывание по ошибке: поле в `/api/instance/info` или в ответе голосового токена.

### 12.4. Веб-клиент: зритель (все платформы)

Эта часть нужна всем — браузеру, Electron и нативному клиенту, — потому что смотреть стрим из оболочки будут с любого клиента. Она выкатывается раньше, чем оболочка начнёт так стримить.

- **Свернуть «стрим» во владельца в одном месте** — там, где `useLiveKit` строит список участников (`ParticipantInfo`): участник с атрибутом `streamOf` не попадает в списки, счётчики и плитки участников, а его дорожки экрана и звука экрана становятся дорожками владельца. Всё, что ниже (плитка стрима, громкость звука стрима, «смотрю», качество приёма, статистика, индикатор «в эфире»), продолжает работать с владельцем и о втором участнике не знает.
- **Адресация.** Указатели, запросы «смотрю» и сигналы стрима адресуются identity пользователя, а не «стрима»: их принимает и отправляет страница владельца. Проверить каждое место, где identity берётся у участника дорожки (`streamPointerProtocol`, `streamWatchProtocol`, протокол обнаружения зрителей из `sounds.md`).
- **Подписка.** Подписка на дорожки «стрима» управляется так же, как на стрим обычного участника (только когда смотрят).
- **Старый клиент** (федеративный собеседник с сервера без правки, вкладка с устаревшим кэшем) видит «стрим» отдельным участником с именем владельца и пометкой. Это деградация вида, не потеря функции.

### 12.5. Веб-клиент: ведущий в нативной оболочке

- **Экран настройки.** Плитки источников — как сейчас. «Начать»: запрос пропуска стрима у сервера звонка → `startNativeScreenShare` в оболочку с адресом LiveKit, пропуском, источником и настройками качества → состояние «в эфире» по ответу оболочки. До «Начать» в звонок ничего не уходит и соединение стрима не поднимается.
- **Превью до старта** — решение владельца (12.9): снимки выбранного источника от оболочки раз в секунду-две либо живая картинка нативным слоем поверх окна.
- **Собственная плитка стрима** показывает стрим так же, как у зрителя: подпиской на дорожку «стрима» с сервера. Отдельного локального пути для превью нет; ведущий видит ровно то, что видят зрители.
- **Настройки посреди стрима** (разрешение, частота, битрейт, режим «текст/движение», «Звук системы», смена источника) — `updateNativeScreenShare`; переопубликация только там, где без неё нельзя (смена кодека).
- **Статистика отправки** («Сведения о соединении»: битрейт, кадры/с, размер, кодек, аппаратный ли кодировщик, пинг, потери) приходит событием от оболочки и ложится в существующее окно.
- **Остановка и сбои.** Стоп из интерфейса, событие сервера, закрытие источника, отозванное разрешение, потеря соединения стрима — у каждого свой исход и своё сообщение; голос при сбое стрима не трогается.
- **Кодек.** Выбор — «Авто», H.264, H.265 (12.12); VP9 клиент не публикует. «Авто» в нативном клиенте — H.265 с резервной дорожкой H.264 для зрителей, которые H.265 не умеют (`preferredBackupCodec`).
- Исправления для WebKit от 2026-11-19 (`hwOverdrive.appliesTo`, потолок в `applyOverdrive`) остаются: они нужны Safari и запасному пути через захват WebKit.

### 12.6. Оболочка

- **Зависимость.** `client-sdk-swift` (LiveKit, Apache-2.0) как зависимость пакета; она приносит готовую сборку WebRTC (`LiveKitWebRTC`, двоичный фреймворк). Обоснование: своё соединение со звонком и аппаратное кодирование внутри WebRTC иначе пришлось бы писать самим. Версия закрепляется; проверки зависимостей и лицензий в CI распространяются на `Package.resolved`; фреймворк встраивается в бандл и подписывается (`bundle.sh`, `sign.sh`), размер приложения вырастет — измерить.
- **Сборка.** Пакет собирается инструментами Xcode 27.2 (`DEVELOPER_DIR`); цель сборки поднимается до macOS 26 (ограничение «до 15» было от SDK Command Line Tools). CI: проверить, какой Xcode на раннере.
- **Сеанс стрима** (`ShareSession`): подключение по пропуску, публикация дорожки экрана из собственного захвата (`SystemScreenCapturer` → источник кадров библиотеки), публикация звука системы (`SystemSoundCapturer` → библиотека), слежение за размером окна (уже есть), исключение окна указателей из захвата (уже есть), переподключение, остановка, статистика. За протоколом (`ScreenSharePublisher`), чтобы логика оболочки проверялась без сети подставной реализацией.
- **Один стрим на окно.** Одновременных захватов для превью больше нет (их требовала старая схема).

### 12.11. Ответы пробы (2026-11-19)

Инструмент `StreamProbe` (цель пакета, `Sources/StreamProbe`) подключается к комнате тестового сервера по пропуску из файла, публикует дорожку экрана из кадров, которые подаёт сам (выдуманных или с настоящего дисплея через `SystemScreenCapturer`), и звук готовыми отсчётами; вторым процессом подключается зрителем. Раз в секунду печатает то, что сообщает WebRTC. Библиотека — `client-sdk-swift` 2.19.0 (WebRTC 150.7871.4); сервер LiveKit 1.9.11; MacBook с дисплеем 3456×2234, туннель владельца включён.

**1. Сборка.** Собирается и инструментами Xcode 27.2 (Swift 6.4.2), и Command Line Tools (Swift 6.1.2); тесты пакета проходят. **Но работает только сборка инструментами Xcode:** собранный Command Line Tools инструмент падает (segmentation fault) при входе в комнату, причина не разбиралась. Значит, приложение с этой библиотекой собирается только Xcode, и это же относится к раннеру CI. Библиотека приносит два динамических фреймворка: `LiveKitWebRTC` (29 МБ, arm64 и x86_64 вместе) и `RustLiveKitFFI` (3 МБ). Скачиваемый архив WebRTC — 686 МБ на все платформы. Битрейт на одной и той же картинке: H.264 4–8 Мбит/с, H.265 3,1–4,2 Мбит/с на родном размере; 4–5 против 1,4 Мбит/с на 1440p. **Не измерено:** зритель на Chromium (Electron, браузер) — это шаг В, в нём же проверяется резервная дорожка.

**3. Звук** (пробел с меткой закрыт форком, шаг Г0)**.** Режим библиотеки без устройств (`AudioManager.setManualRenderingMode`) плюс подача готовых отсчётов (`mixer.capture(appAudio:)`): звук доходит до зрителя (48 кбит/с, уровень у зрителя равен поданному), устройство ввода не открывается, разрешение на микрофон не запрашивается (до и после — «не спрашивалось»). **Пробел:** открытый API создаёт звуковую дорожку только с меткой «микрофон»; метку «звук экрана» (`screen_share_audio`) задать нельзя. По пропуску, который разрешает только экран и звук экрана, такая дорожка не опубликуется. В самой библиотеке есть черновик ровно про это (PR #1084, отдельная звуковая дорожка с меткой «звук экрана»), он ждёт выпуска WebRTC.

**4. Смена посреди стрима** (пробел с битрейтом закрыт форком, шаг Г0)**.** Частота и размер кадра следуют за тем, что подаёт оболочка, без переопубликации: зритель увидел 3456×2234 → 1728×1116 на той же дорожке. **Пробел:** потолок битрейта после публикации открытым API не меняется (внутренний пересчёт параметров читает настройки, с которыми дорожка опубликована). Резервный кодек библиотека умеет (`preferredBackupCodec`: H.264 или VP8 при основном H.265, VP9, AV1).

**5. Сетевой путь.** Соединение оболочки идёт напрямую по UDP; пинг 4–9 мс при включённом туннеле — как у Electron (5 мс) и против 90–160 мс у страницы в WebKit. Провалов соединения за ~30 прогонов не было.

**Находка сверх вопросов.** В 4 прогонах из ~30 оценка канала в первую секунду оказывалась 0,7–1,5 Мбит/с и росла примерно на 8 % в секунду; кодировщик на это время выбрасывал кадры (2–30 кадров/с вместо 60). От кодека, звука и зрителя не зависит. Канал при этом не узкий: в прогоне VP9 оценка дошла до 17 Мбит/с. В Electron от такого защищает нижняя граница битрейта («overdrive»); в открытом API библиотеки её нет. Библиотека позволяет подставить собственный кодировщик H.264 и H.265 (`videoEncoderFactory`) — это запасной способ держать границу без правки библиотеки.

**Вторая находка (2026-11-19, длинные прогоны): подстройка WebRTC под «перегрузку» режет частоту зря.** Прогоны пробы короче 40 секунд этого не показывали. С настройкой по умолчанию для стрима («держать размер, снижать частоту») примерно на 40-й секунде WebRTC снижает частоту с 60 до 40 кадров/с с причиной «ограничено процессором» и обратно не поднимает; при любой нагрузке от соседних программ — ещё на ступень, до 26. Процесс при этом занимает 3–6 % одного ядра. Причина: детектор перегрузки считает загрузкой время прохождения кадра через аппаратный кодировщик (39 мс на кадр при интервале 16,7 мс), хотя кодировщик выдаёт все 60 кадров. Проверено парой прогонов по 70 секунд без зрителя: по умолчанию — 60 кадров до 40-й секунды, дальше 40; с отключённой подстройкой (`DegradationPreference.disabled`) — 60 кадров все 70 секунд, при большей загрузке машины. **Требование к шагу Г:** оболочка публикует стрим с отключённой подстройкой; размером и частотой она управляет сама. Это же объясняет «ограничено процессором» в логе ведущего во время проверки зрителя в браузере. Открытый вопрос для приёмки: сами 39 мс задержки в кодировщике (первые секунды — 11 мс) входят в строку «задержка» таблицы против Electron.

### 12.12. Кодек: только H.264 и H.265 (решение владельца от 2026-11-19)

Владелец, прочитав замеры 12.11: «H.265 и VP9 примерно равны — тогда полностью отказываемся от VP9, на выбор оставляем только H.264 и H.265».

**Что публикует клиент.** Выбор в настройках стрима — «Авто», H.264, H.265, на всех клиентах. VP9 клиент больше не публикует; AV1 не появляется. **Смотреть VP9 клиент по-прежнему умеет:** старые версии и федеративные собеседники на них публикуют VP9 ещё долго, декодирование ничего не стоит.

**«Авто»:**

1. H.265, если эта машина кодирует его аппаратно и сервер звонка его принимает; зрителю, который H.265 не умеет, сервер запрашивает резервную дорожку H.264, и она кодируется только пока такой зритель смотрит.
2. Иначе H.264: аппаратно там, где есть аппаратный кодировщик, программно там, где нет никакого.
3. Что кодировщик оказался не тем, которого ждали (программным), проверяется по статистике после публикации, как сейчас делает `screenShareCodec.ts`; при программном H.265 выбор исправляется на H.264.

**Явный H.265** показывается только там, где он кодируется аппаратно. Пункта, который можно выбрать и получить вместо него другое, быть не должно.

| Клиент | H.264 | H.265 | «Авто» |
|---|---|---|---|
| Нативный macOS | аппаратно (измерено) | аппаратно (измерено) | H.265 с резервной H.264 |
| Electron и Chromium, macOS и Windows | аппаратно | зависит от версии Chromium и видеокарты, **не измерено** | H.264, пока H.265 не измерен; затем по правилу |
| Firefox, Linux, машины без аппаратного кодировщика | программно | нет | H.264 программный |

**Цена решения, сказанная вслух.** Там, где аппаратного кодировщика нет вовсе, «Авто» сегодня берёт VP9; после решения это программный H.264. Он легче для процессора, чем программный VP9, но на тот же битрейт даёт картинку хуже. Матрица битрейтов веб-клиента подобрана под VP9 и пересматривается под H.264 и H.265 в шаге И — там же замер.

**Проверить до включения H.265 в «Авто»** (шаг В): что зритель на Chromium (Electron, браузер) декодирует H.265 с сервера, и что зритель без H.265 (Firefox) получает резервную дорожку H.264.

Справка по исходной посылке: по трафику H.265 и VP9 примерно равны (H.265 обычно чуть экономнее), оба заметно экономнее H.264. По нагрузке на Mac H.264 и H.265 стоят одинаково (оба аппаратные); VP9 программный и на порядок дороже — в пробе 2,5 ядра против 0,1–0,2.
